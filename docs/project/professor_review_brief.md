# 무장애·가족 친화 관광 챗봇 시제품 검토 자료

마지막 갱신: 2026-05-17

## 1. 검토 목적

**검토받고 싶은 핵심**

- **시연 적합성**: 현재 완성도가 공모전 시연용 MVP로 충분한가
- **제품 범위**: 무장애 관광 추천에 집중하고, 의료·예약·실시간 정보는 제외하는 판단이 맞는가
- **기술 구조**: TourAPI, 로컬 fallback, RAG, 규칙 기반 처리와 ML 보조 신호의 조합이 타당한가
- **품질 근거**: 자동 eval, 실제 브라우저 QA, blind eval 결과를 발표에서 어떻게 설명할까
- **표현 방식**: 접근성 정보를 “보장”이 아니라 “공식 데이터 기반 추천”으로 안내하는 방식이 충분히 안전한가

## 2. 한 줄 요약

> 한국관광공사 무장애 여행 정보와 로컬 RAG/fallback 자료를 결합해, 지역·접근성 조건을 이해하고 근거가 있는 관광지 카드를 추천하는 상담형 시제품이다.

현재 문서는 공모전 시연 범위와 후속 검수 범위를 교수님께 확인받기 위한 검토 자료다. 단순히 LLM을 붙인 챗봇이 아니라, 자연어 의도와 대화 문맥을 따로 분석하고 그 결과를 추천 품질 평가에 연결했다는 점을 설명한다.

## 4. 기술 구조

| 요소 | 역할 |
|---|---|
| FastAPI | `/tourism/chat`, `/tourism-ui/`, 상태 확인 API 제공 |
| TourAPI | 한국관광공사 무장애 여행 정보 후보와 상세 접근성 정보 조회 |
| 로컬 fallback | API 실패·쿼터·네트워크 불안 시에도 응답 가능한 Markdown 카드 |
| ChromaDB/RAG | 저장된 관광 카드와 문서를 검색해 후보 근거 확보 |

| ML 보조 분류기 | 의도/문맥 판단 보조. 규칙을 대체하지 않고 헷갈리는 표현을 확인 |
| LLM 추론 보조 | 기본 OFF. 켜도 후보 생성이 아니라 카드 재랭킹/확인 메모 보조로 제한 |

응답 흐름:

```text
질문
-> 지역/조건/후속 의도 해석
-> 모호 지역이면 선택 질문
-> cache / RAG / fallback 후보 확인
-> 부족하거나 사용자가 요청하면 live TourAPI 보강
-> 조건 근거가 있는 카드만 추천
-> 출처, 주의 문구, 후속 제안 반환
```

## 5. 사용자 경험

시연 화면은 `/tourism-ui/`다.

- 기본 개발 모드: API 주소, Swagger/ReDoc/OpenAPI, DBG 진단 패널 노출

## 7. 자연어 처리와 ML 활용

질문을 그대로 LLM에 넘기지 않고, 먼저 아래 정보를 분리해 처리한다.

- 사용자가 원하는 행동: 추천, 더 보기, 조건 변경, 제외, 최신 조회 등
- 이어받을 대화 조건: 지역, 접근성 조건, 가족/이동 편의, 제외 선호
- 추천 제어 방식: 규칙 기반 처리를 중심으로 두고, ML은 보조 신호로 사용
- 평가 방식: 라벨 점수와 실제 chat 카드 품질을 분리해 확인

### 7.1 의도 분류

- 목적: 사용자의 다음 행동을 분류한다.
- 대상: `추천`, `더 보기`, `최신 정보`, `조건 추가`, `조건 교체`, `조건 제외`, `지역 변경`, `미지원 요청`.
- 데이터: 자체 발화, AI Hub 관광 대화 추출 발화, 경계 사례, 실제 chat 평가셋.
- 현재 적용: 규칙 기반 처리가 주도하고, 문자 n-gram Naive Bayes는 보조 신호로 사용한다.
- 예시: `오늘 환율 알려줘`는 비관광 요청으로 차단한다.
- 예시: `응급실은 말고 관광지만 계속`은 부정 표현을 보고 관광 문맥을 유지한다.

| 항목 | 지표 | 결과 |
|---|---|---:|
| 의도 분류 학습셋 | 학습 row 수 | 16,254 rows |
| 내부 holdout | accuracy | 0.9164 |
| AI Hub/adversarial holdout | accuracy | 0.9229 |
| Gemini verified holdout | accuracy | 0.8536 |
| hard intent holdout | accuracy | 0.9747 |
| region clarify natural holdout | accuracy | 0.9800 |
| change/replace 실제 chat holdout | 자동 채점 통과율 | 201/201 |
| adversarial chat holdout | 자동 채점 통과율 | 42/42 |

### 7.2 문맥 해석

- 목적: 추천 결과를 바꾸는 조건 해석을 분리한다.
- strict 조건: `둘 다`, `반드시`처럼 모든 조건이 필요한 요청.
- soft 조건: `가능하면`, `있으면 좋고`처럼 완화 가능한 요청.
- OR 조건: `수어 또는 자막`처럼 둘 중 하나면 되는 요청.
- 조건 교체: `유모차 말고 휠체어`처럼 기존 조건을 바꾸는 요청.
- 조건 제외: `시장 말고`, `카페 제외`처럼 빼야 하는 선호.
- 시설 근거: 휠체어, 유모차, 수유실, 점자블록, 가족 편의처럼 카드 근거가 필요한 요청.

| 접근 | 역할 |
|---|---|
| rule-only | 명시 표현을 직접 처리하는 기준선 |
| Naive Bayes | 가벼운 문자 n-gram baseline |
| LinearSVC | sparse text feature 기반 선형 분류 |
| LogisticRegression | 확률 기반 선형 분류 |
| hybrid LinearSVC / LogisticRegression | 규칙 결과와 선형 모델 결합 |
| KLUE-RoBERTa small | transformer fine-tuning 후보 |
| SuperGemma4 selective labeling | 오답 재라벨링과 검수 보조 실험 |

| 평가 | 결과 |
|---|---:|
| context locked test 최신 | micro-F1 0.9803 |
| independent validation 최신 | micro-F1 0.9741 |
| specific-facility adversarial | micro-F1 0.9946 |
| rotating blind v4 rule-only | micro-F1 0.9091 |
| rotating blind v4 hybrid LinearSVC | micro-F1 0.9012 |
| rotating blind v4 hybrid LogisticRegression | micro-F1 0.8968 |
| 실제 chat blind v2 | 15/15 통과 |

지표 해석:

- v1/v2/v3: 발견한 오류를 고친 뒤의 회귀 점검 결과.
- v4 blind: 새 평가셋 기준으로 일반화 가능성을 확인한 결과.
- v4에서는 rule-only가 hybrid LinearSVC/LogisticRegression보다 조금 높았다.
- 현재 런타임은 복합 ML 모델로 교체하지 않는다.
- 규칙 기반 처리를 중심에 두고, ML은 보조 신호로 유지한다.
- 실제 chat blind v2 15/15 결과를 함께 보고 카드 품질을 확인한다.

### 7.3 Transformer와 LLM 채택 판단

- KLUE-RoBERTa small fine-tuning도 비교했다.
- validation micro-F1은 0.9241이었다.
- locked test 단독 micro-F1은 0.8594였다.
- rule hybrid micro-F1은 0.9474였다.
- 기존 기준선을 넘지 못했고, 응답 지연도 더 길었다.
- 따라서 런타임 교체는 보류했다.
- SuperGemma4 selective labeling은 일부 exact를 올렸지만 micro-F1이 하락했다.
- SuperGemma4는 런타임 판단자가 아니라 QA/재라벨링 보조로 둔다.
- 결론: 현재 구조는 **규칙 기반 처리 + ML 보조 신호 + 실제 chat 평가** 조합이다.
- LLM은 후보 생성 엔진이 아니라, 필요할 때 카드 순서와 설명을 보조하는 역할로 제한한다.

### 7.4 현재 런타임에서 쓰는 방식

현재 챗봇은 룰셋만으로 동작하지 않는다. 다만 최종 행동 결정의 중심은 규칙 기반 처리이고, ML과 RAG는 아래 위치에서 보조한다.

| 구성 | 실제 역할 |
|---|---|
| 규칙 파서 | 지역, 조건, 제외, 교체, 더 보기, 최신 조회, 미지원 요청을 1차 판단 |
| 의도 분류기 | 문자 n-gram Naive Bayes. 짧은 후속 발화가 어떤 행동인지 보조 판단 |
| 문맥 라벨 분류기 | strict/soft/OR/교체/제외/가족/이동/시설 근거 라벨을 보조 판단 |
| RAG/Chroma 검색 | 저장된 관광 카드와 문서에서 후보를 찾고 추천 근거 확보 |
| TourAPI/로컬 카드 | 휠체어, 주차, 화장실, 수유실, 점자블록 등 접근성 근거 확인 |
| LLM | 기본 OFF. 켜도 후보 생성이 아니라 재랭킹, 설명, 검수 보조로 제한 |

실제 처리 흐름은 다음과 같다.

1. 규칙 파서가 지역과 명시 조건을 먼저 잡는다.
2. 의도 분류기가 `더 보기`, `조건 교체`, `조건 제외`, `지역 변경` 같은 후속 의도를 보조한다.
3. 문맥 라벨 분류기가 `둘 다 필요`, `가능하면`, `수어 또는 자막`, `시장 제외` 같은 조건 해석을 보조한다.
4. RAG와 TourAPI/로컬 카드에서 근거 있는 후보만 가져온다.
5. 카드 근거와 실제 chat 평가로 결과가 맞는지 확인한다.

따라서 현재 구조는 **룰셋 단독**이 아니라, **규칙 기반 제어 + ML 보조 신호 + RAG/구조화 데이터 근거 확인** 조합이다. 다만 한국어의 우회 표현과 생략을 더 잘 다루려면 실제 사용자 발화와 LLM 생성 발화를 이용해 라벨을 확장하고, 이후 룰셋 함수 또는 Transformer 계열 분류기로 고정하는 방향이 필요하다.

## 8. 시연에서 강조할 차별점

1. **근거 기반 카드 추천**
   - 장소명만 추천하지 않고, 휠체어·주차·화장실·수유실·점자블록 등 확인된 근거를 카드에 붙인다.

2. **지역 오인 방지**
   - `중구`처럼 여러 지역에 있는 이름은 바로 추천하지 않고 선택 질문을 한다.

3. **좁은 지역 자동 확장 금지**
   - 사용자가 시군구를 명시하면 다른 지역을 임의로 섞지 않는다.
   - 부족하면 부족 안내와 근처/주변 확장 제안을 한다.

4. **후속 질문 처리**
   - `더 보기`, `그중 시장 말고`, `유모차 말고 휠체어`, `서울 중구 말고 부산 중구` 같은 흐름을 유지한다.

5. **환각 억제**
   - 근거가 없으면 카드를 억지로 만들지 않고, 조건 완화나 지역 확장을 제안한다.

6. **ML/NLP 기반 개선 과정**
   - 의도 분류, 문맥 라벨, 새 평가셋, 실제 chat 평가를 분리해 단순 프롬프트 수정이 아니라 반복 가능한 검증 흐름을 만들었다.

7. **시연 안정성**
   - live API가 불안해도 fallback/RAG로 기본 시연이 가능하다.

## 10. 교수님께 확인받고 싶은 질문

이 검토 자료에서는 관광 추천 챗봇을 구성하는 데이터 검색, 자연어 처리, ML 및 Transformer 계열 실험, 실제 chat 평가의 연결 방식이 타당한지 확인받고자 한다.

현재 구조는 다음 흐름이다.

<!-- spacer -->

- 후보 확보: TourAPI와 RAG/fallback으로 근거 있는 관광 카드를 찾는다.
- 문맥 해석: 규칙 기반 처리와 ML 보조 분류기로 의도와 조건을 해석한다.
- 모델 비교: Naive Bayes, LinearSVC, LogisticRegression, Transformer를 비교해 런타임 채택 여부를 판단한다.
- 품질 확인: 같은 평가셋을 보고 보강한 결과와, 처음 보는 새 문장·실제 chat 응답 평가를 분리해 확인한다.

이 흐름을 기준으로 아래 내용을 확인받고 싶다.

<!-- spacer -->

1. RAG, TourAPI, fallback을 함께 쓰는 구조가 관광 추천 챗봇의 근거성과 안정성을 높이는 방향으로 타당한가?
2. 의도 분류와 문맥 해석을 LLM 프롬프트에만 맡기지 않고 별도 규칙/ML 단계로 분리한 판단이 적절한가?
3. 규칙 기반 처리를 중심에 두고 ML 분류기를 보조 신호로 쓰는 현재 구조가 실무적으로 설득력 있는가?
4. 규칙 기반 기준선은 무장애 관광 시연 범위에서 지역·접근성 조건·제외·교체 표현을 직접 정의한 결과다. 새 문장 평가에서는 rule-only micro-F1 0.9091, hybrid LinearSVC 0.9012, hybrid LogisticRegression 0.8968이었고, Transformer도 locked test 단독 micro-F1 0.8594로 기존 구조를 넘지 못했다. 다만 한국어는 우회 표현과 생략이 많아 규칙만으로는 편협해질 수 있다. 이 결과를 “현재 범위에서는 규칙 중심 유지, 장기적으로는 발화 수집과 라벨 확장 필요”로 해석하는 것이 타당한가?
5. 오류를 발견한 평가셋에서 다시 점수가 오른 결과는 회귀 점검으로 보고, 처음 보는 새 문장과 실제 챗봇 응답 카드로 별도 확인했다. 이런 평가 방식이 특정 단어와 규칙에만 맞춰지는 문제를 줄이는 데 충분한가, 아니면 실제 사용자 발화 수집을 더 우선해야 하는가?
6. LLM을 후보 생성 엔진이 아니라 재랭킹, 설명, 검수 보조로 제한한 방향이 RAG 챗봇 구조에 맞는가?
7. 앞으로 보강한다면 데이터 품질 검수, 문맥 평가셋 확장, 모델 고도화, 운영 로그 분석 중 무엇을 우선해야 하는가?

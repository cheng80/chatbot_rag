# 무장애·가족 친화 관광 챗봇 시제품 검토 자료

마지막 갱신: 2026-05-15

## 1. 검토 목적

**검토받고 싶은 핵심**

- **범위**: 2026-06-10까지의 시제품 범위가 현실적인가
- **구조**: RAG, TourAPI, LLM 사용 구조가 타당한가
- **일정**: 데이터 수집·평가·시연 준비에서 줄일 것과 남길 것이 무엇인가
- **발표**: 강조할 차별점이 무엇인가

## 2. 요약

> **핵심 문장**: 일반 RAG 문서 검색 챗봇을 기반으로, 한국관광공사 OpenAPI와 로컬 벡터 검색 자료를 결합해 **무장애·가족 친화 관광지를 근거 기반 카드로 추천하는 상담형 시제품**을 만든다.

**현재 검증 초점**

- **접근성 조건**: 휠체어, 유아차, 고령자, 어린 자녀 동반
- **지역명 모호성**: `중구`, `남구`처럼 여러 지역에 있는 지명
- **환각 억제**: 근거 부족 시 `확인 필요` 또는 `결과 부족` 표시
- **시연 화면**: 카드, 출처, 주의 문구를 웹에서 확인

## 3. 기술 구조

| 요소 | 프로젝트 내 역할 |
|---|---|
| **RAG** | 관광 Markdown/문서를 먼저 검색해 답변 근거로 사용 |
| **LLM** | 후보 장소를 만들지 않고, 후보 카드의 순서·상담 문장·확인 메모만 보조 |
| **임베딩/ChromaDB** | 질문·문서를 벡터화하고 로컬 벡터DB에서 유사도 검색 |
| **TourAPI** | 한국관광공사 OpenAPI. 캐시/RAG에 없을 때만 실시간 조회 |
| **캐시/폴백** | 반복 API 호출을 줄이고, 실패 시 미리 수집한 자료로 응답 유지 |
| **eval/이벤트 로그** | 20문항 평가와 질문-카드 연결 기록으로 품질 분석 |

응답 흐름:

```text
질문 -> 지역/조건/확장 의도 구조화 -> 모호 지역이면 선택 후보 반환
-> 카드 캐시 확인 -> RAG/ChromaDB 검색 -> 없으면 TourAPI 조회
-> 관광지 카드 생성 -> 필요 시 LLM 보조 -> 답변/카드/출처/주의 문구 반환
```

> **기본 전략**: **캐시/RAG 우선 + 부족할 때 TourAPI live-on-miss**.  
> 매번 API를 호출하지 않고, 저장 자료와 검색 자료를 먼저 사용한다.

## 4. 범위

**포함**

- **질문 처리**: 자연어 관광 질문, 지역/조건/확장 의도
- **데이터 경로**: TourAPI 조회, RAG 검색, 폴백 자료
- **시연 화면**: 웹 확인 화면, 지역 선택 버튼, 추천 카드
- **품질 검증**: pytest, 20문항 eval, 이벤트 로그

**제외/후순위**

- 일정 자동 생성, 예약/결제, 모바일 앱 완성
- 전국 모든 관광지 전체 수집
- 정식 운영 대시보드
- 일반 관광 전체 확장, 병원/약국/응급의료기관 결합

## 5. 주요 설계 결정

| 결정 | 이유와 보완 |
|---|---|
| **캐시/RAG 우선** | 호출량 절약과 시연 안정성. 데이터 신선도는 주기적 갱신으로 보완 |
| **좁은 지역 자동 확장 금지** | 사용자가 요청한 지역을 임의로 넓히지 않음. 부족하면 부족 안내 |
| **동명이 지역 추가 질문** | `중구`, `남구` 등 지역 오인 방지. UI에서 빠른 선택 버튼 제공 |
| **가족 호칭만으로 고령자 추정 금지** | 휠체어 사용자를 고령자로 단정하지 않음. 명시 조건만 처리 |
| **LLM은 상담 보조로 제한** | 환각 방지. 후보 카드 밖의 장소·접근성 정보 생성 금지 |
| **의료 안전 정보는 후속 확장** | 가치가 크지만 최신성·책임 범위 부담. 위치/운영 정보 안내로 제한 |

## 6. 현재 구현·데이터 상태

| 영역 | 상태 |
|---|---|
| 서버/API | **`/tourism/chat` 구현**, 안전한 오류 응답, 진단 정보, 이벤트 로그 |
| 데이터/RAG | TourAPI 후보 조회, 무장애 상세 조회, ChromaDB 검색, Markdown 폴백 |
| 지역 처리 | 동명이 지역 추가 질문, 행정동/법정동 매칭 데이터 |
| 웹 확인 | 자유 질문, 지역 선택 버튼, 카드 표시, Help 팝업, Swagger/ReDoc 링크 |
| 테스트/eval | **자동 테스트 72개 통과**, 20문항 fallback-only 1차 실행, **API 실패 0건** |
| 모델 비교 | SuperGemma, Gemma4, Qwen3 후보 1차 비교 |

**데이터 수치**

- 미리 수집한 관광 자료: **643개**
- ChromaDB 색인: **644개 문서 / 650개 조각**
- 중복 콘텐츠ID: **16개 분석 후 0개로 정리**
- TourAPI 지역 코드: **234개 기준**
- 3장 이상 확보 시군구: **161개**
- 시군구 3장 목표 남은 부족분: **약 182장**

**진행도 요약**: 시제품 전체 **80%**, 서버 응답 계약 **90%**, 웹 시연 화면 **70%**, 품질 평가 **70%**, 운영 준비 **20%**.

## 7. 품질 개선 작업

| 작업 | 목적 |
|---|---|
| **샘플 감사·중복 정리** | 필드 누락, 파싱 실패, 중복 콘텐츠ID 점검 |
| **행정동/법정동 매칭** | `좌동`, `마산합포구`, `분당구` 같은 실제 표현 처리 |
| **동명이 지역 clarification** | `중구`, `남구` 등 지역 오인 방지 |
| **안전한 오류·폴백 진단** | 내부 예외 노출 방지, OpenAPI/RAG 실패 상태 표시 |
| 이벤트 로그 | 질문과 추천 카드 매칭 분석 기반 마련 |
| 모델 벤치마크 | LLM 보조의 품질·지연 시간 확인 |
| 웹 테스트 화면 | 비개발자도 카드/출처/주의 문구 확인 가능 |

## 8. LLM 모델 판단

| 모델 | 1차 판단 |
|---|---|
| **현재 SuperGemma 기본 모델** | 한국어 상담 기본 후보. 별도 사고 과정은 미지원 |
| `gemma4:e4b` | native thinking 가능하나 **30초 이상 지연** |
| `huihui_ai/gemma-4-abliterated:e4b` | native thinking 가능하나 지연과 안전 필터 약화 검토 필요 |
| `qwen3:4b` | thinking은 가능하나 현재 JSON/한국어 계약 준수 부족 |

> **현재 방침**: 짧은 LLM 보조 방식 유지, **후보 카드 밖 정보 생성 금지**, 모델 내부 사고 과정 비노출.

## 9. 남은 작업

**공개 데모 전 필수**

- **20문항 eval 수동 채점** 및 live-on-miss 재실행
- **부족 지역 보강**, 모바일/외부 접속 점검
- 대표 화면 캡처, **시연 모드 결정**

**품질 보강**

- 전국 실사용 지역 250개 기준 재정리
- 시군구 폴백 부족분 보강
- TourAPI 영속 캐시 설계
- 이벤트 로그 SQLite 전환 검토

**후순위**

- 모바일 앱 전환, 주기적 데이터 갱신, 정식 배포
- 관리자 대시보드, 병원/약국/응급의료기관 결합 검토

## 11. 교수님께 확인받고 싶은 질문

1. **범위**: 시제품 범위가 2026-06-10까지 현실적인가?
2. **구조**: 캐시/RAG 우선 + TourAPI live-on-miss 전략이 공모전 목적에 맞는가?
3. **지역 정책**: 동명이 지역 추가 질문과 좁은 지역 자동 확장 금지 정책이 사용자 관점에서 타당한가?
4. **LLM 경계**: LLM을 후보 생성자가 아니라 상담 보조로 제한하는 방향이 적절한가?
5. **발표 차별점**: 환각 억제, 출처 기반 카드, RAG/폴백 안정성, 지역명 현실성, eval 기반 검증 중 무엇을 전면에 둘까?
6. **후속 확장**: 일반 관광과 병원/약국 안전 정보 확장을 후속 연구·개발 방향으로 두는 판단이 적절한가?

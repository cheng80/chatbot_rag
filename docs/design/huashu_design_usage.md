# Huashu Design 스킬 사용법

마지막 갱신: 2026-05-18

이 문서는 `alchaincyf/huashu-design` 스킬을 Codex에서 사용할 때의 설치 상태, 용도, 사용 방식, 우리 무장애 관광 챗봇 프로젝트에 적용할 때의 주의점을 정리한다.

## 설치 상태

- 설치 방식: GitHub 저장소를 Codex 글로벌 스킬 폴더에 설치
- 설치 위치: `$CODEX_HOME/skills/huashu-design`
- 원본 저장소: `https://github.com/alchaincyf/huashu-design`
- 라이선스: MIT

Codex는 새로 시작한 뒤 글로벌 스킬 목록을 다시 읽는다. 설치 직후 현재 세션에서는 스킬 트리거가 바로 보이지 않을 수 있으므로, 실제 사용 전에는 Codex를 재시작하는 것이 안전하다.

## 어떤 스킬인가

Huashu Design은 HTML을 산출 매체로 사용하는 디자인 스킬이다. 단순 웹 페이지 제작보다 다음 작업에 맞춰져 있다.

- 고충실도 앱/웹 프로토타입
- 클릭 가능한 모바일 앱 mockup
- HTML 기반 발표 deck
- 디자인 방향 탐색과 여러 시안 비교
- 모션 디자인, MP4/GIF 내보내기
- 인포그래픽, 데이터 시각화
- 5차원 디자인 리뷰

중요한 전제는 “HTML은 도구이고, 결과물은 디자인 산출물”이라는 점이다. 즉 생산용 웹앱 코드를 바로 만드는 스킬이라기보다, 디자인 시안·프로토타입·발표물·시각 자료를 빠르게 만드는 데 적합하다.

## 언제 쓰면 좋은가

우리 프로젝트에서는 다음 상황에 유용하다.

- 옵션형 추천 모드의 화면 흐름을 여러 시안으로 보고 싶을 때
- 모바일 우선 앱 화면 mockup이 필요할 때
- 교수님 설명용 시각 자료나 발표용 HTML deck이 필요할 때
- 현재 `/tourism-ui/`와 다른 레이아웃 실험을 빠르게 보고 싶을 때
- 카드 UI, 조건 선택 UI, 빈 결과 회복 UI의 시각적 대안을 비교하고 싶을 때

반대로 다음에는 우선순위가 낮다.

- FastAPI API 계약 변경
- 실제 `/tourism/chat` 로직 변경
- 접근성 데이터 정규화
- ML/NLU 평가 및 학습
- production frontend 코드의 직접 수정

## 기본 사용 요청 예시

Codex 재시작 후 다음처럼 직접 요청한다.

```text
huashu-design 스킬을 사용해서 무장애 관광 추천 앱의 옵션형 추천 모드 프로토타입을 만들어줘.
모바일 우선 화면 5개로 구성하고, 지역 선택, 관광 유형, 동반 상황, 접근성 조건, 필수/선호 조건, 추천 결과, 빈 결과 회복 액션을 포함해줘.
```

디자인 방향을 먼저 비교하고 싶을 때:

```text
huashu-design 스킬로 무장애 관광 챗봇의 디자인 방향 3가지를 제안하고,
각 방향마다 대표 화면 1개씩 HTML mockup으로 만들어줘.
현재 앱은 메신저형 상담 UI이고, 새 디자인 실험은 Flutter 이전 가능성을 고려해 Material 3 Expressive 기반의 부드러운 녹색 tonal UI를 기준으로 한다. 과한 랜딩 페이지식 hero는 피해야 한다.
```

현재 앱 개선 시안을 만들 때:

```text
huashu-design 스킬로 현재 /tourism-ui/의 개선 시안을 만들어줘.
기존 API 계약과 카드 렌더링 구조는 바꾸지 않고,
조건 확인 버튼, 카드 근거 칩, 빈 결과 회복 버튼, 지역 확장 버튼을 더 읽기 쉽게 배치하는 방향으로 비교 시안을 만들어줘.
```

교수님 설명용 시각 자료가 필요할 때:

```text
huashu-design 스킬로 무장애 관광 챗봇의 처리 흐름을 설명하는 HTML 발표 deck을 만들어줘.
자연어 입력, 조건 정규화, RAG/검색, 카드 추천, 추가 질문, 옵션형 추천 모드를 6장 내외로 설명해줘.
```

## 우리 프로젝트 기준 프롬프트

디자인 작업을 시작할 때 다음 문서를 먼저 참조하도록 지시한다.

```text
다음 문서들을 기준으로 디자인해줘.

- docs/project/app_design_planning_context.md
- docs/design/tourism_chatbot_DESIGN.md
- docs/tourism/tourism_service_enhancement_ideas.md
- docs/tourism/option_flow_app_concept.md

기존 /tourism-ui/의 API 계약과 카드 렌더링 로직은 유지한다.
디자인 산출물은 실제 구현 전 검토용 HTML 프로토타입으로 만들고,
프로덕션 코드 반영은 별도 승인 후 진행한다.
```

## 디자인 품질 기준

Huashu Design의 원래 철학 중 우리 프로젝트에 맞는 기준만 적용한다.

- 기존 문서와 현재 앱 맥락에서 출발한다.
- 구체적 제품·기술·최신 정보가 필요하면 먼저 확인한다.
- 의미가 애매한 사용자 입력은 단정하지 않고 추가 질문으로 유도한다.
- 앱 프로토타입은 실제 클릭 흐름을 가져야 한다.
- 디자인 산출물은 Playwright 등으로 화면이 깨지지 않는지 확인한다.
- 과한 보라색 그라디언트, 의미 없는 장식, generic AI mockup 느낌을 피한다.
- 과한 유리 효과나 투명도보다 가독성, 큰 터치 타깃, 명확한 상태 표현을 우선한다.
- 접근성 정보는 추측하지 않고 “확인 필요” 상태를 유지한다.

## 적용 절차

1. 디자인 목적을 정한다.
   - 옵션형 추천 모드
   - 현재 채팅 UI 개선
   - 발표 deck
   - 카드 UI 비교

2. 참조 문서를 지정한다.
   - `docs/project/app_design_planning_context.md`를 기본 컨텍스트로 둔다.

3. HTML 프로토타입을 만든다.
   - 이 단계에서는 `frontend/web` 생산 코드를 바로 수정하지 않는다.

4. 화면을 눈으로 검토한다.
   - 모바일 폭과 데스크톱 폭을 모두 확인한다.
   - 버튼, 카드, 말풍선, 입력창이 겹치지 않는지 본다.

5. 구현 후보만 선별한다.
   - API 계약 변경이 필요한 요소는 보류한다.
   - 정적 mockup에서만 가능한 장식은 제거한다.
   - 기존 `/tourism-ui/`와 잘 맞는 컴포넌트만 반영한다.

6. 별도 구현 작업으로 옮긴다.
   - 구현 시에는 기존 테스트와 브라우저 QA를 다시 수행한다.

## 주의점

- Huashu Design은 강한 디자인 방향을 제안할 수 있지만, 결과가 항상 우리 서비스 UX에 맞는 것은 아니다.
- 디자인 산출물의 HTML을 그대로 `frontend/web`에 복사하지 않는다.
- 우리 앱은 실제 추천 카드와 API 응답 상태를 다루므로, mockup의 더미 데이터와 운영 로직을 구분해야 한다.
- 옵션형 추천 모드는 규모가 큰 기능이므로 별도 진입점 또는 섹션으로 분리해서 도입한다.
- 디자인이 좋아 보여도 카드 근거, 출처, 방문 전 확인 안내, 빈 결과 회복 액션은 반드시 유지한다.

## 재설치 또는 제거

재설치가 필요하면 기존 폴더를 제거한 뒤 다시 설치한다.

```bash
rm -rf "$CODEX_HOME/skills/huashu-design"
```

그 뒤 원본 저장소를 다시 글로벌 스킬 폴더에 설치한다. 설치 후 Codex를 재시작해야 한다.

# 5번 확장안: 채팅형/선택형 무장애 관광 추천 모드

## 목적

이 문서는 `docs/tourism/tourism_service_enhancement_ideas.md`의 **5. 옵션형 추천 모드**를 현 시점 기준으로 확장한 상세 기획이다.

현재 `/tourism-ui/`는 자연어 채팅을 기본 입력으로 사용한다. 1-4번 보강안인 조건 확인, 카드 근거 표시, 데이터 부족 회복 버튼, 지역 확장 정책이 1차 반영되면서 채팅형 UX의 안정성은 높아졌다. 5번 옵션형 추천 모드는 이 흐름을 대체하는 별도 앱이 아니라, 1-4번에서 만든 정책과 컴포넌트를 재사용하는 **입력 방식 확장**으로 설계한다.

즉 핵심은 “챗봇 앱 vs 선택형 앱”의 분리가 아니라, 하나의 무장애 관광 추천 앱 안에서 사용자가 `채팅형`과 `선택형`을 전환할 수 있게 하는 것이다.

목표는 세 가지다.

- 문장을 쓰기 어려운 사용자에게 안정적인 조건 입력 경로를 제공한다.
- 공모전/발표 시연에서 같은 입력이 같은 조건으로 처리되는 재현성을 높인다.
- 자연어 NLU를 버리지 않고, 선택형으로 만든 조건을 채팅형 결과 카드와 같은 렌더링/회복 정책에 연결한다.

## 현재 기준

5번은 아래 구현 완료 항목 위에 올라간다.

- 애매한 표현은 `clarification` 응답과 선택 버튼으로 확인한다.
- 카드 본문은 조건별 정보를 `라벨 + 설명` 행으로 일관되게 보여준다.
- 카드가 없으면 `이 조건으로 다시 찾기`, `같은 시·도까지 넓히기`, `조건 완화하기`를 중복 없이 제안한다.
- `근처`, `주변`, `가까운`, `인근`은 자동 광역 확장 신호로 쓰지 않는다.
- `부족하면 서울 전체로 넓혀줘` 같은 조건부 확장은 요청 시군구 후보가 기본 표시 수인 5장보다 부족할 때만 실행한다.
- `서울 전체로 넓혀줘` 같은 무조건 확장은 사용자가 명시한 것으로 보고 상위 지역 후보를 섞는다.
- 추천 결과가 길어도 제출 후 스크롤은 결과 상단에 머문다.
- 지역·예시 선택은 하단 고정 입력창 안에서 접힘 패널로 제공한다.

## 제품 방향

선택형 모드는 앱 전체를 바꾸는 별도 화면이 아니라, 하단 입력부 또는 답변 상단에서 전환 가능한 `입력 방식`이다. 기존 채팅형을 유지하면서 조건 입력만 더 안정적으로 만드는 확장이다.

```text
[ 채팅형 ] [ 선택형 ]
```

채팅형은 지금처럼 문장을 입력한다. 선택형은 단계별 선택지를 통해 같은 `/tourism/chat` 요청 문장을 만든다. 백엔드 API 계약은 유지한다. 즉 선택형도 최종적으로는 구조화 데이터를 직접 POST하지 않고, 현재 API가 이해할 수 있는 자연어 문장 또는 후속 질문 문장을 생성해 보낸다.

이 방식의 장점은 다음과 같다.

- 백엔드 계약 변경 없이 빠르게 도입할 수 있다.
- 기존 세션 맥락, 카드 렌더링, 출처, 회복 버튼, 지역 확장 정책을 그대로 재사용한다.
- 선택형 UI가 만든 문장도 이벤트 로그와 기존 평가 흐름에 남는다.

장기적으로는 `/tourism/chat`이 구조화 요청도 받을 수 있게 확장할 수 있지만, 1차 구현에서는 API 계약을 바꾸지 않는다.

## 화면 구조

### 1. 모드 전환

하단 composer 상단 또는 `지역·예시 선택` 접힘 패널 안에 segmented control을 둔다.

- `채팅형`: 현재 자유 입력창, 지역·예시 선택, 추천 받기 버튼
- `선택형`: 단계별 조건 builder

모드 전환은 현재 입력값을 파괴하지 않는다. 채팅형에서 쓰던 문장은 유지하고, 선택형에서 만든 조건은 입력창에 요약 문장으로 반영한다.

### 2. 선택형 조건 builder

선택형은 한 화면 안의 접힘/스텝 구조로 둔다. 모바일에서는 세로 스텝, 데스크톱에서는 좁은 wizard 패널로 표시한다.

1. 지역
   - 광역 시·도
   - 시군구
   - 동명이 지역은 목록에서 선택하게 하며, 자연어 모호성은 UI에서 제거한다.

2. 동행 상황
   - 휠체어 이용
   - 유모차/영유아 동반
   - 어르신/보행 부담
   - 시각장애 접근성
   - 청각장애 접근성
   - 보조견/안내견 동반

3. 접근성 조건
   - 휠체어 접근
   - 입구/동선 접근로
   - 장애인 화장실
   - 장애인 주차
   - 엘리베이터/승강
   - 대중교통 접근
   - 점자/촉지 안내
   - 오디오/음성 안내
   - 수어/자막/문자 안내
   - 수유실/기저귀 교환대

4. 조건 강도
   - 꼭 필요
   - 있으면 좋음

   1차 구현에서는 모든 선택 조건을 기존 자연어 조건으로 변환한다. `꼭 필요`와 `있으면 좋음`은 UI 상태로만 보관하고, 문장에는 `둘 다`, `필수`, `있으면 좋고` 같은 표현을 붙여 기존 parser가 해석하게 한다.

5. 선호/제외
   - 실내
   - 조용한 곳
   - 공원/산책
   - 박물관/전시
   - 시장 제외
   - 음식점/카페 제외
   - 숙박 제외
   - 오래 걷는 코스 제외

6. 지역 확장 방식
   - 요청 지역만 먼저 보기
   - 부족하면 같은 시·도까지 보기
   - 지금 같은 시·도까지 넓혀 보기

이 항목은 최신 정책을 그대로 반영한다. `부족하면`은 조건부 확장이고, 지역 후보가 충분하면 확장하지 않는다.

## 선택값에서 요청 문장 만들기

1차 구현은 구조화 API가 아니라 문장 생성 방식으로 간다.

예시 1:

```json
{
  "area": "서울",
  "sigungu": "강남구",
  "conditions": ["휠체어 접근", "장애인 화장실"],
  "required": true,
  "expansion": "conditional"
}
```

요청 문장:

```text
서울 강남구에서 휠체어 접근과 장애인 화장실 둘 다 있는 관광지 추천해줘. 부족하면 서울 전체로 넓혀줘
```

예시 2:

```json
{
  "area": "제주",
  "sigungu": "제주시",
  "conditions": ["수어 안내", "점자 안내"],
  "required": true,
  "expansion": "local_only"
}
```

요청 문장:

```text
제주시 안에서 수어 안내와 점자 안내가 모두 있는 곳만 보여줘
```

예시 3:

```json
{
  "area": "부산",
  "conditions": ["유모차"],
  "preferences": ["실내"],
  "excluded": ["시장"]
}
```

요청 문장:

```text
부산에서 유모차로 가기 좋은 실내 관광지 추천해줘. 시장은 제외해줘
```

## 자연어 입력의 위치

선택형 안에서도 자연어는 보조 모드로 둔다.

버튼명:

```text
자연어로 조건 추가
```

사용자가 복합 상황을 입력하면 바로 검색하지 않고 해석 결과 확인 화면을 보여준다.

예:

```text
입력: 엄마가 오래 못 걸어서 많이 안 움직이는 곳이면 좋겠어
해석 결과:
- 동행 상황: 어르신/보행 부담
- 선호 조건: 짧은 동선
- 확인 필요: 실제 휴식 공간 여부는 카드 근거가 부족할 수 있음
```

사용자는 `적용`, `수정`, `취소` 중 하나를 고른다. 이 흐름은 현재 `clarification` 정책과 같은 철학이다. 모델이 단정하지 않고 사용자 확인을 거친다.

## 결과 화면 연결

선택형 결과도 채팅형 결과와 같은 컴포넌트를 쓴다.

- 답변 말풍선
- 추천 카드
- 카드별 `라벨 + 설명` 근거 행
- 출처
- 방문 전 확인 안내
- `더 보기`
- `최신 정보 더 찾기`
- 빈 결과 회복 버튼

다만 선택형에서 만든 조건은 답변 상단에 작은 요약 바를 보여줄 수 있다.

```text
조건: 서울 강남구 · 휠체어 접근 · 장애인 화장실 · 부족하면 서울 전체
```

이 요약 바는 정보 확인용이지 별도 필터 UI가 아니다. 수정 버튼을 누르면 선택형 builder로 돌아간다.

## 빈 결과 정책

선택형 모드도 현재 빈 결과 정책을 그대로 따른다.

- 같은 조건으로 다시 찾기
- 같은 시·도까지 넓히기
- 조건 완화하기

`조건 완화하기`는 조건을 임의로 삭제하지 않는다. 선택형 builder로 돌아가 `꼭 필요` 조건 일부를 `있으면 좋음`으로 옮기거나, 무장애 기본 조건으로 낮추는 제안을 보여준다.

예:

```text
수어 안내 + 점자 안내 모두 필수 조건에서는 제주시 후보가 없습니다.
아래 중 하나를 선택하세요.
```

- 같은 조건으로 다시 찾기
- 제주 전체로 넓히기
- 점자/수어 중 하나만 필수로 바꾸기
- 무장애 기본 조건으로 보기

## 디자인 기준

현재 앱 디자인과 충돌하지 않게 한다.

- 하단 composer는 계속 유지하되, 선택형 builder가 항상 펼쳐져 카드 영역을 잡아먹지 않게 한다.
- 선택형은 접힘 패널, bottom sheet, 또는 대화 영역 안의 한 말풍선형 wizard로 구현한다.
- 첫 화면을 랜딩 페이지로 만들지 않는다.
- UI 카드는 8px 안팎의 절제된 radius를 우선하되, 기존 앱의 큰 앱 프레임과 톤은 유지한다.
- 버튼은 텍스트만 길게 나열하지 않고, 단계별 선택 칩과 체크 상태를 명확히 구분한다.
- 조건 선택지는 많은 수가 한꺼번에 보이지 않게 카테고리별로 묶는다.
- 모바일에서 입력창과 선택 패널이 카드 영역을 과도하게 가리지 않게 한다.

## 1차 구현 범위

1차는 5번 확장의 최소 기능으로 도입한다. 1-4번 기능을 다시 만들지 않고, 선택형 입력이 기존 채팅형 결과 흐름으로 들어가게 하는 데 집중한다.

- `채팅형 / 선택형` segmented control
- 선택형 접힘 패널
- 지역 선택
- 동행 상황 선택
- 접근성 조건 다중 선택
- 조건부/무조건 지역 확장 선택
- 선택값을 자연어 요청 문장으로 변환
- 기존 `/tourism/chat` 호출
- 결과 카드 렌더링 재사용

1차에서 제외한다.

- 백엔드 구조화 요청 API 신설
- 저장/공유
- 사용자 접근성 프로필 저장
- 복잡한 자연어 보조 해석 화면
- 필수/선호 조건의 완전한 랭킹 모델 반영

## 2차 구현 후보

- 필수/선호 조건 분리 UI 고도화
- 자연어 조건 추가 해석 확인 화면
- 제외 조건 세분화
- 조건 요약 바에서 즉시 수정
- 빈 결과에서 조건 완화 후보를 자동 구성
- 선택형 플로우 이벤트 로그
- 향후 Flutter 전환을 고려한 상태 모델 정리

## 구현 메모

현재 `frontend/web`는 정적 HTML/CSS/JS 구조다. 따라서 1차 구현은 다음 파일 중심으로 한다.

- `frontend/web/index.html`: 모드 전환과 선택형 패널 템플릿
- `frontend/web/styles.css`: segmented control, 선택형 wizard, 모바일 레이아웃
- `frontend/web/app.js`: 선택 상태 관리, 문장 생성, 기존 submit 흐름 연결
- `frontend/web/README.md`: QA 항목 추가
- `tests/test_tourism_chat_service.py`, `tests/test_tourism_query_service.py`: 선택형이 만드는 대표 문장 정책 검증

서버 API를 바꾸지 않는 한 FastAPI 쪽 변경은 최소화한다.

## 판정

옵션형 추천 모드는 이제 별도 앱 후보가 아니라 현재 채팅형 앱을 보강하는 두 번째 입력 방식으로 보는 것이 맞다. 사용자는 빠르게 말하고 싶으면 채팅형을 쓰고, 조건을 확실히 고르고 싶으면 선택형을 쓴다. 두 모드는 같은 추천 결과 컴포넌트와 같은 정책을 공유해야 한다.

가장 먼저 만들 것은 완전한 설문 앱이 아니라, 하단 입력부에서 전환 가능한 작은 선택형 조건 builder다.
